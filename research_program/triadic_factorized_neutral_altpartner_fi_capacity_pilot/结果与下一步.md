# 全信息观察容量 pilot：设计校正与结果状态

## 状态

这批 8 种子运行**不作为 FI 证据**。训练和数值审计均完成，但事后代码核对发现：pilot 的 `runner.py` 把 `x_FI` 重命名为 `x_PL` 后复用 PL 版 `source_runner.remap_batch`。因此 `static` 四臂使用了 FI 输入，而 `rematched` 四臂在重配时按 PL 规则清除了其他人的需求块；四臂并非同一 FI 观察权限。原始运行、失败记录、checkpoint、审计和统计全部保留，不能把其主量解释为 FI 的重配×通信效应。

## 原始运行记录（仅作失效材料）

独立种子 66721–66728 比较了 `static/rematched × live/silent`，共 32 次训练、192 个 checkpoint。原始 JSON 汇总给出目标搭档率主量 **−15.8116 pp**（t7 区间 [−16.2118,−15.4114]），但该数值混合了 static-FI 与 rematched-PL 输入，现标记为 **invalid_by_information_remap**，不进入论文统计或跨批次合并。原始四格末点和次量仍可在 [原始汇总](results/fi_001/aggregation_001/results.json) 中复核。

训练后的源配对辅助函数按 64 次运行的旧假设退出；32 个 per-run JSON、全部 checkpoint 和 training log 均已写出，随后用 JSON-only 恢复，没有修改 checkpoint 或日志。恢复、聚合和图表过程的数值审计仍通过：192 个 checkpoint、32,348,160 个训练布局世界、307,307,520 次模块前向，`max_abs_error=0`；但这些检查只能证明计算与保存文件一致，不能修复信息权限错误。NumPy 2.5 的 `np.trapz` 兼容别名只用于聚合，未新增前向或更新。

## 纠正后的结论

这批 pilot 不能收窄“PL 看不到其他需求”的解释，也不能与正式 16 种子 FI 批次比较。正确的 FI 重配必须在重配后保留并重新排列全部三人的需求块；正式批次 `triadic_factorized_neutral_altpartner_information_control_study` 使用独立 FI remap，并以 16 个种子作为信息权限结果。该 pilot 的失效记录保留用于防止重复设计错误。

后续信息权限分析只使用正式 FI 批次及已审计 PL 批次：先在训练前检查每个 schedule 的观测块、重配映射和 FI 标志，再进行 PL/FI/closed-channel 对照。该 pilot 不提供词义、组合语法、公共词典、代际传递或人类语言起源证据。
