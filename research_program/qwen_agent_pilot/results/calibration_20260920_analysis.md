## 运行记录

本次为筛查性校准，不是确认性检验。方案在采集前冻结于 Git commit `99e8d90dd877f31150a83d786951f18207aa1ffc`，见 [`calibration_plan.md`](../calibration_plan.md)。模型为 `mlx-community/Qwen3.5-9B-8bit`，固定 revision `16daa4818c54ce5f5436f929d52542eb65bbed9d`。三个种子（20260921–20260923）各含空信道、已知共享码本、自由符号三个配对条件；每个单元36轮，共324轮、972次模型调用。采集时间约41.5分钟。

逐轮数据、消息、动作和反馈保存在 [`calibration_20260920.json`](calibration_20260920.json)，文件校验值见 [`calibration_20260920_manifest.json`](calibration_20260920_manifest.json)。文件不含模型原始 completion 或思维文本。已逐轮重放生成器并复算324个环境结果；同一种子三个条件的场景、请求者、含义、目标物品完全一致。所有324个 owner JSON、648个 helper JSON/action 均通过格式校验；码本臂108/108次选出正确编码。

## 解释与下一步

自由符号条件没有稳定提高联合协作成功；第二种子虽出现较高的消息—含义互信息，第三种子却塌缩为单一字符串，且三个种子的成功率都很低。空信道也偶有成功，说明联合成功存在随机基线。

本轮暴露出更直接的环境问题：提示允许 helper “行动或等待”，但没有明确说明每个订单只有一个指定搭档可以行动、其他搭档必须等待。已知码本臂中，两位 helper 常对同一目标做出完全相同的行动。这使团队成功率同时测量消息解码与未明确写出的行动分工规则，不能把两者混为语言形成结果。

因此 v1 仅作为诊断记录。下一版在三个条件中一致、明确地写出单人负责规则，并要求无法识别自己是否被指定时等待；先用未纳入正式矩阵的开发种子检查已知码本正对照。如果正对照能稳定通过，再冻结新协议、换用未见种子重做配对矩阵。v1 数据保留，不与修订版合并分析。
